# 서울 상권 입지판단 본체 알고리즘 및 점수산정 명세

작성일: 2026-06-26

## 1. 결론

입지 판단 본체는 `scripts/build_location_judgement_engine.py`로 구현했다.

입력은 사용자가 선택한 위치, 예산, 업종이다. 현재 구현에서는 위치를 다음 세 방식으로 받을 수 있다.

| 입력 방식 | 우선순위 | 설명 |
|---|---:|---|
| `trade_area_code` | 1 | 상권코드 직접 매칭. 가장 안전함 |
| `trade_area_name` | 2 | 상권명 부분 문자열 매칭. 동명이 있을 수 있음 |
| `lat`, `lng` | 3 | 상권 중심점 최근접 매칭. 현재는 폴리곤 포함 판정이 아니므로 경고 출력 |

업종은 다음 방식으로 받는다.

| 입력 방식 | 우선순위 | 설명 |
|---|---:|---|
| `industry_code` | 1 | 서비스 업종 코드 직접 매칭. 가장 안전함 |
| `industry_name` | 2 | 업종명 부분 문자열 매칭. 보조용 |

최종 출력은 text model에 넣기 쉬운 JSON이다. 변수 키는 영어 중심이고, 설명 내용과 경고는 한국어로 나온다.

## 2. 본체가 하는 일과 하지 않는 일

### 하는 일

- 상권-업종-분기 단위 데이터를 정확히 찾는다.
- 최신분기 기준으로 같은 업종 또는 전체 상권과 비교한다.
- 각 지표를 0~100 백분위 점수로 바꾼다.
- 업종별 가중치를 적용한다.
- 데이터 신뢰도와 경고를 붙인다.
- text model이 리포트를 쓸 때 지켜야 할 금지 규칙을 JSON에 같이 넣는다.

### 하지 않는 일

- 개별 매장의 성공 가능성을 보장하지 않는다.
- 없는 월세, 권리금, 순이익, 손익분기 값을 만들지 않는다.
- 최신분기 `다음분기_매출` 빈 값을 실측값처럼 쓰지 않는다.
- 모델 예측값이나 성공확률을 임의로 만들지 않는다.
- text model에게 숫자 계산을 맡기지 않는다.

## 4. 전체 처리 순서

1. FeatureMart parquet를 읽는다.
2. 입력 위치와 업종을 최신분기 행에 매칭한다.
3. 같은 업종 기준 비교군을 만든다. 같은 업종 행이 너무 적으면 최신분기 전체를 비교군으로 쓴다.
4. 자치구 비교군이 필요한 항목은 자치구 행을 따로 만든다.
5. 각 원천 지표를 백분위로 변환한다.
6. 7개 컴포넌트 점수를 계산한다.
7. 업종별 가중치를 곱해 총점을 만든다.
8. 데이터 신뢰도 게이트를 적용한다.
9. ReportFacts 압축값과 text model용 금지 규칙을 포함한 JSON을 저장한다.

### 5.1 수요 점수

|---|---|---|

목적:

사용 지표:

| 지표 | 방향 | 이유 |
|---|---|---|
| `당월_매출_금액` | 높을수록 유리 | 현재 상권-업종 매출 규모 |

주의:

`매출_전분기_증감률`은 변동성이 크므로 매출 규모와 점포당 매출보다 낮은 내부 비중으로 반영한다.

목적:

점포가 많아서 생기는 집객 효과와 동일 업종 과밀 위험을 함께 본다.

사용 지표:

| 지표 | 방향 | 이유 |
|---|---|---|
| `점포당_매출` | 높을수록 유리 | 경쟁을 이기고 남는 매출 효율 |
| `유사_업종_점포_수` | 낮을수록 유리 | 직접 경쟁 압력 |

주의:

점포 수는 무조건 감점하지 않는다. 상권 밀집은 경쟁이면서 동시에 집객 효과일 수 있기 때문이다.

## 6. 정규화 방식

각 원천 지표는 다음 방식으로 백분위 점수로 바꾼다.

```text
백분위 = 비교군에서 현재 값보다 작거나 같은 행의 비율 * 100
```

높을수록 좋은 지표는 그대로 쓴다.

```text
점수 = 백분위
```

낮을수록 좋은 지표는 뒤집는다.

```text
점수 = 100 - 백분위
```

이 방식을 쓴 이유:

- 매출, 인구, 점포 수처럼 단위가 다른 값을 같은 0~100 점수로 비교할 수 있다.
- 같은 업종 안에서 현재 후보가 어느 정도 위치인지 설명하기 쉽다.
- text model이 계산을 하지 않아도 evidence에 원값과 백분위가 들어간다.

## 7. 최종 점수식

최종 점수는 컴포넌트 점수와 업종별 가중치의 곱을 더한 값이다.

```text
최종점수 =
  수요점수 * 수요가중치
+ 매출점수 * 매출가중치
+ 경쟁점수 * 경쟁가중치
+ 접근성점수 * 접근성가중치
+ 성장안정성점수 * 성장안정성가중치
+ 예산리스크점수 * 예산리스크가중치
+ 데이터신뢰도점수 * 데이터신뢰도가중치
```

등급:

| 점수 | 등급 | 해석 |
|---:|---|---|
| 85 이상 | A | 매우 우수. 그래도 현장 확인 필요 |
| 75 이상 | B+ | 조건부 긍정 |
| 65 이상 | B | 보통 이상, 현장 확인 필요 |
| 55 이상 | C | 주의 필요 |
| 55 미만 | D | 낮은 적합도 |

## 9. 10회 알고리즘 재검토 기록

| 회차 | 검토 내용 | 결정 |
|---:|---|---|
| 1 | ReportFacts 단위 확인 | 상권-업종-분기를 본체 grain으로 고정 |
| 2 | 위치 입력 방식 검토 | 상권코드 우선, 좌표는 중심점 최근접 경고 포함 |
| 3 | 업종 입력 방식 검토 | 업종코드 우선, 업종명은 보조 매칭 |
| 4 | 단일 점수 위험 검토 | 총점만 내지 않고 7개 컴포넌트로 분해 |
| 5 | 단위 다른 지표 합산 문제 검토 | 모두 백분위 점수로 변환 후 합산 |
| 6 | 경쟁 지표 방향 검토 | 유사 업종 수와 폐업률은 역방향, 점포 수는 집객 보조 |
| 7 | 예산 지표 한계 검토 | 월세/권리금 부재로 낮은 가중치와 경고 처리 |
| 8 | 데이터 결측 검토 | 데이터 신뢰도 점수와 최종 점수 상한 게이트 추가 |
| 9 | 별도 예측모델 사용 여부 검토 | 현재 제품 경로에서는 사용하지 않고 공공데이터 기반 점수로 고정 |
| 10 | text model 환각 위험 검토 | must_use, must_not_do, recommended_sections를 JSON에 포함 |
| 11 | 샘플 실행 검토 | 이태원 관광특구/한식음식점 샘플 JSON 생성 및 검증 |

## 10. 출력 JSON 스키마 요약

최상위 구조:

```json
{
  "schema_version": "seoul_location_judgement.v1",
  "created_at": "생성시각",
  "language": "ko",
  "request": {},
  "matched_target": {},
  "score_result": {},
  "reportfacts_compact": {},
  "warnings": [],
  "text_model_payload": {}
}
```

text model은 다음 필드만 사용해야 한다.

- `matched_target`
- `score_result.components.evidence`
- `reportfacts_compact`
- `warnings`

text model 금지 사항:

- 없는 숫자 생성
- 출처 없는 주장
